# 낚시 출조 도우미 Agent

*Created At: 2026-11-04T07:12:59.679338+00:00*

## Goal

방파제·갯바위·좌대를 다니는 입문~중급 생활낚시인과 선상낚시 예약 희망자가 흩어진 포인트·날씨·물때·금어기 정보를 한곳에서 확인하고, 결정적 기준에 따라 출조 여부를 판단하며, 사용자 승인(HITL) 기반으로 가상 선상 예약까지 할 수 있게 한다.

## User Stories

1. **As a** 입문~중급 생활낚시인, **I want to** 날짜·권역·낚시 형태·대상 어종을 말하면 출조지 상위 3곳을 추천받고 싶다, **so that** 흩어진 포인트·날씨 정보를 직접 비교하지 않고도 갈 곳을 정할 수 있다.
2. **As a** 입문~중급 생활낚시인, **I want to** 특정 포인트와 날짜의 출조 가능 여부를 가능/주의/불가로 판정받고 싶다, **so that** 풍속·파고·특보·물때를 근거로 안전하게 출조 여부를 결정할 수 있다.
3. **As a** 생활낚시인, **I want to** 어종별 금어기와 포획금지체장을 묻고 싶다, **so that** 규정 위반 없이 낚시할 수 있다(참고용 정보로 활용).
4. **As a** 선상낚시 예약 희망자, **I want to** 배·날짜·인원·예약자 정보를 주고 가상 선상 예약을 승인 후 진행하고 싶다, **so that** 출조 판정과 좌석 상황을 확인한 뒤 안심하고 예약할 수 있다.
5. **As a** 재방문 사용자, **I want to** 이전에 말한 선호 어종·권역·낚시 형태를 다시 말하지 않고 추천을 받고 싶다, **so that** 반복 입력 없이 맞춤 추천을 받을 수 있다.
6. **As a** 생활낚시인, **I want to** 추천 뒤 '거기 물때는?'처럼 이어서 질문하고 싶다, **so that** 대화 흐름을 유지하며 자연스럽게 정보를 얻을 수 있다.

## Constraints

- 데이터는 전국 4개 권역(서해·남해·동해·제주)의 가상 데이터이며, 2026-11-06~08 스냅샷만 지원한다.
- 판정 기준은 data/criteria.json을 그대로 사용하며 수정하지 않는다. 기준값은 교육용 가상값이다.
- 지원하는 특보는 없음, 풍랑주의보, 풍랑경보, 태풍경보뿐이다. 강풍주의보는 데이터에 없다.
- 결제는 하지 않고 예약번호만 발급한다. 예약 시 원본 데이터는 바꾸지 않는다.
- 낚시 규정 RAG 답변은 참고용이며 실제 법령 확인이 필요하다는 안내를 붙인다.
- 출항 시각은 데이터에 없으므로 승인 화면에 표시하지 않는다.
- 예약자 이름과 전화번호는 장기 기억에 저장하지 않는다.
- 장기 기억은 SQLite에 user_id별로 저장한다.
- LLM Judge는 temperature=0으로 설정하고 케이스당 1회만 실행해 채점한다.
- 평가는 사람이 하지 않고 run_eval.py 자동 평가 스크립트와 LLM Judge가 함께 판정한다.
- 현재 Seed에서는 평가셋(test_queries.csv)을 변경하지 않는다.

## Success Criteria

1. 출조 판정: 풍속과 파고가 모두 '가능' 상한 이하이면 가능, 모두 '주의' 상한 이하이면 주의, 그 외에는 불가로 판정한다. 상한(가능 / 주의)은 방파제·좌대 8m/s·1.5m / 11m/s·2.0m, 갯바위 6m/s·1.0m / 9m/s·1.5m, 선상 7m/s·1.0m / 10m/s·1.5m이다.
2. 출조 판정: 풍랑주의보가 있으면 선상·갯바위는 불가, 방파제·좌대는 최소 주의로 판정한다. 풍랑경보·태풍경보가 있으면 모든 유형을 불가로 판정한다. 수치 판정과 특보 판정 중 더 나쁜 쪽을 따른다.
3. 출조 판정: 물때가 사리이면 갯바위와 선상의 '가능'을 '주의'로 낮춘다(예: 갯바위 9m/s·1.6m·사리 → 불가).
4. 추천: 어종·시즌·권역·낚시 형태로 후보를 거른 뒤 '가능'을 '주의'보다 앞에 두고, 등급이 같으면 spot_id 순으로 정렬해 최대 3곳을 보여 준다. 풍속·파고 여유는 순위에 반영하지 않는다.
5. 추천: '불가' 포인트는 후보에서 빼고 제외 사유만 언급할 수 있다. 가능·주의 포인트가 3곳 미만이면 있는 만큼만 보여 주고, 다른 권역이나 다른 날짜를 대안으로 제시하지 않는다.
6. 예약: 배ID·날짜·인원·예약자 이름·전화번호가 모두 모일 때까지 예약 도구를 호출하지 않으며, 빠진 정보는 거절하지 않고 되묻는다.
7. 예약: 승인 직전에 배 이름과 ID, 날짜, 인원, 1인 가격과 총액, 마스킹된 예약자 정보, 그날의 출조 판정을 안내 문구와 함께 보여 준다.
8. 예약: 'y'나 '승인' 같은 명시적 승인만 승인으로 처리한다. 그 밖의 응답이나 수정 요청은 거부로 보고, 예약을 만들지 않은 채 취소 문구를 보여 준 뒤 종료한다. 평가할 때는 자동으로 승인한다.
9. 예약: 그날 선상 판정이 '불가'이면 예약을 막고, '주의'이면 확인 내용에 주의 경고를 덧붙여 진행한다.
10. 예약: 인원이 남은 좌석보다 많으면 남은 좌석 수를 알리고 인원 조정을 안내한 뒤 예약을 거절한다. 같은 날 다른 배는 제안하지 않는다.
11. 개인정보 마스킹: 이름은 홍*동(두 글자 이름은 홍*), 전화번호는 010-****-5678 형식으로 가리며, answer·contexts·trace·로그 모두에 적용한다.
12. 장기 기억: 선호 어종·권역·낚시 형태만 user_id별로 저장하고, 추천 도구가 호출될 때 갱신한다. 세션이 바뀌거나 서버를 재시작해도 유지한다.
13. 장기 기억: 기억한 선호를 사용할 때는 답변에 '이전에 말씀하신 ○○·○○ 기준'처럼 근거를 밝힌다.
14. 2턴 후속 질문: 같은 thread의 대화 기억으로 '거기' 같은 지칭 대상을 해석하고, 도구를 다시 호출해 답한다.
15. 없는 포인트: 고정 문구 SPOT_NOT_FOUND로 알리고 지원 4개 권역을 안내하며, 특정 대안 포인트는 추천하지 않는다.
16. 범위 밖 날짜: 고정 문구 DATE_OUT_OF_RANGE로 지원 기간(2026-11-06~08)을 밝히고 판정하지 않는다. 가장 가까운 날짜로 대신 판정하지 않는다.
17. 규정에 없는 어종: '규정 문서에서 찾을 수 없음'과 참고용 안내(실제 법령 확인 필요)를 함께 보여 주고, 수치를 추측해 제시하지 않는다.
18. 모호한 포인트: 후보를 최대 3곳까지 보여 주고 되묻는다. 선호나 기억을 근거로 임의로 하나를 고르지 않는다.
19. 가드레일: 범위 밖 질문과 프롬프트 인젝션을 거절하고, trace에 guardrail_input 단계가 남는다. 불가 판정 시에는 강행을 권하지 않는다.
20. 평가: 인-아웃 세트 15건(positive 6, negative 3, edge 4, guardrail 2) 중 13건 이상 통과한다. 반드시 통과해야 하는 케이스는 두지 않는다.
21. 평가 케이스 통과 조건: ① expected_tools가 실제로 호출된 도구에 포함된다. ② forbidden 항목을 어기지 않는다(문자열 항목은 코드로, [판단] 항목은 LLM Judge로 검사). ③ LLM Judge가 expected_traits를 모두 충족했다고 판정한다. 정확한 문자열 일치는 요구하지 않는다.

## Assumptions

- 수익 모델은 선상 예약 중개 수수료이며, 실제 수익 검증은 출시 이후 PM이 후속으로 할 일로 수락 조건에 포함하지 않는다.
- SERVICE.md의 '판정·안전 케이스 전부 통과'는 합격 조건이 아니라 서비스 유용성을 판단하는 보조 지표로만 사용한다.
- 개인정보 마스킹은 별도 케이스 없이 예약 케이스 2건(6번, 13번)에서 함께 검증된다.
- 상세 결정 사항은 SERVICE.md와 .ouroboros/seed.yaml에 기록된 내용과 일치한다고 가정한다.
- 평가셋의 expected_tools·forbidden·expected_traits가 위 요구사항을 충분히 반영하도록 작성되어 있다고 가정한다.
